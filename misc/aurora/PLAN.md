# План Godot 4.7.2 для ОС Аврора

Дата: 23 октября 2026. Статус: проектирование; порт не собран и не проверен на устройствах.

## Цель и принятые решения

- Репозиторий движка: https://github.com/KotDath/godot.
- Ветка реализации: `4.7.2_auroraos` от официального `4.7.2-stable`, коммит `ed1daf0bf001b61586d9930840f2f1394092c079`.
- Самостоятельная платформа `platform=auroraos`, а не флаг `auroraos=yes` у LinuxBSD.
- Обязательны ARM32 и ARM64, запуск игр и работа самого редактора на Авроре.
- Обязательны создание и загрузка GDExtension, адаптация https://github.com/KotDath/godot-cpp, корректная линковка SO и включение зависимостей в RPM.
- Архитектуру не привязываем к номеру релиза Авроры. Выбор возможностей — по протоколам, API, ABI и драйверам. Конкретные sysroot и toolchain обязательно фиксируются для воспроизводимости; независимость архитектуры от версии ОС не означает бинарную совместимость любых сборок.
- Базовый рендерер — Compatibility / GLES3. Vulkan добавляется после аппаратной проверки. GLES2 требует отдельного проекта и не входит в этот план.
- Редактор на устройстве должен создавать, импортировать, редактировать, сохранять и запускать проекты. Сборка C++ расширений и подписанных RPM непосредственно на устройстве — отдельный сценарий, не подразумеваемый наличием редактора. Первичный инструментарий разработки расширений работает на компьютере.

## Результаты анализа savegame

Исследована ветка `savegame/godot:4.4_auroraos`, вершина `6f208cf0a4433625a87d18f0d05cb7d13ac2bbe2`. От базы `6f7daa23fb` — 12 коммитов, 33 изменённых файла, 3217 добавлений и 44 удаления. В `version.py` — `4.4.2-rc`.

Реализация использует LinuxBSD с `auroraos=yes`: Wayland, выключенные X11/libdecor/ALSA, изменения EGL/libhybris, touch, ориентация, PulseAudio, полноэкранное окно, однооконный редактор, экспорт RPM. Добавлены `wl_shell` и `qt_surface_extension` для композиторов без нужной поддержки XDG shell.

Не переносить патчи вслепую:

- `platform/auroraos/detect.py` содержит старые параметры `bits`, `tools`, `release_debug`, Bullet и SDL2; это не готовая платформа для Godot 4.7.
- Touch и `text-input-v3` уже реализованы в Wayland backend 4.7.2. Нужен анализ пробелов, а не дублирование старой реализации.
- Поворот изображения содержит большой Aurora-специфичный блок в общем GLES-рендерере.
- Изменения общего EGL/Vulkan поведения требуют узких условий применения и проверки Linux.
- В изменённой загрузке курсоров присутствует ранний возврат перед основной логикой для не-Aurora сборки.
- Экспортёр около 1600 строк смешивает UI, SDK, упаковку, подпись и выполнение команд.
- В `SConstruct` минимальный SCons снижен с 4.0 до 3.0.5. Это обход проверки, а не доказательство полной совместимости сценариев сборки со старым SCons.

## Что важно в Godot 4.7 / 4.7.2

4.7 приносит AreaLight3D, HDR-вывод, DrawableTexture2D, offset transforms для Control, предпросмотр текстовых шейдеров и обновлённый Asset Store. Возможности конкретного рендерера и GPU проверяются отдельно. 4.7.2 включает 57 исправлений, в том числе ввод, Wayland IME и GDExtension.

В исходниках 4.7.2: `EnsureSConsVersion(4, 4)` и `EnsurePythonVersion(3, 9)`. Linux Wayland EGL запрашивает desktop OpenGL 3.3; для Aurora нужно явно реализовать GLES-контекст. Инициализация Wayland требует `xdg_wm_base`: поддержка legacy shell потребует разделения этого поведения.

## Архитектура платформы

```text
platform/auroraos/
  detect.py, SCsub
  godot_auroraos.cpp
  os_auroraos.{h,cpp}
  display_server_auroraos.{h,cpp}
  egl_manager_auroraos.{h,cpp}
  platform_gl.h, platform_egl.h
  wayland/
    aurora_shell.{h,cpp}
    aurora_text_input.{h,cpp}
    aurora_orientation.{h,cpp}
  services/
    lifecycle.{h,cpp}
    audio_policy.{h,cpp}
  export/
    export.cpp
    export_plugin.{h,cpp}
    rpm_package.{h,cpp}
    native_dependencies.{h,cpp}
    build_environment.{h,cpp}
    templates/
```

Названия файлов предварительные. `OS_AuroraOS` наследуется от `OS_Unix`: пути, идентичность, процессы, жизненный цикл, регистрация драйверов. Не наследовать desktop-предположения Linux автоматически.

Общие соединение Wayland, очередь событий и ввод выделить из `platform/linuxbsd/wayland` в переиспользуемый слой, например `drivers/wayland`. Объём выделения ограничивать реальными потребностями двух платформ. Перемещения файлов и изменения поведения делать отдельными коммитами. Не копировать Linux backend целиком.

- Shell выбирается по registry композитора: XDG либо изолированный legacy backend.
- EGL/GLES: проверка расширений, корректные native handles, fallback для libhybris только при подтверждённой необходимости.
- Ориентация: одна модель преобразования для изображения, размеров окна, touch, мыши и IME. Предпочтение преобразованиям композитора; отдельный blit только если нужен.
- Общий рендерер не должен зависеть от мобильной политики окон. Необходимые hooks должны быть минимальными и пригодными для других платформ.
- PulseAudio переиспользуется; политика ресурсов и жизненного цикла принадлежит Aurora.
- `OS.has_feature("auroraos")`, архитектуры и export feature tags согласованы между runtime, редактором и экспортёром.
- Экспортёр собирается в Linux-редакторе без линковки с целевыми библиотеками Aurora.

## Сборка самого Godot: Python и SCons

Согласованное направление: bootstrap сборочных инструментов вместе с общей сборочной процедурой Godot. Требования upstream не понижать.

```text
исходники host Python + закреплённый SCons
                  ↓ bootstrap
изолированный host-tools prefix
                  ↓
SCons Godot + выбранные target compiler/sysroot
                  ↓
ARM32 / ARM64 editor, template_debug, template_release
```

1. Фиксировать точные версии Python (не ниже 3.9) и SCons (не ниже 4.4), исходные архивы и SHA256. Конкретную пару выбрать по совместимости и проверить в первом эксперименте. Одинаковую проверенную пару применять для движка и godot-cpp.
2. Python собирать для архитектуры и ABI сборочного хоста в изолированный prefix, например `.build/host-tools/<fingerprint>`. SCons — Python-пакет: установить из закреплённого wheel/исходников без необходимости отдельной нативной компиляции.
3. Bootstrap выполняется до входа в режим target-компиляции. Нельзя случайно получить ARM Python для запуска на x86_64. Учитывать host-зависимости CPython; не предполагать, что бинарник с новой glibc хоста запустится в старом SDK chroot.
4. Для SDK/PSDK строить host Python в совместимом host/tooling-контексте среды и проверять его выполнение в выбранном режиме SB2. Если отображение путей SB2 мешает host-инструментам, запускать host SCons с явными wrapper-командами target compiler, linker, ar и pkg-config. Такой fallback сначала проверить на минимальном проекте.
5. Для BT собирать host-tools отдельным слоем поверх зафиксированного Docker-образа. Компиляторы и sysroot брать из BT, а не из дистрибутива контейнера. Поддержать offline-bootstrap из заранее подготовленных исходников/wheel.
6. Явно задавать CC/CXX/AR/RANLIB, sysroot и target pkg-config. Сохранять требуемые флаги target, исключать host include/lib пути. Не переопределять toolchain на основе архитектуры машины, выполняющей Python.
7. Генераторы кода запускаются на хосте; целевые исполняемые файлы не запускаются автоматически во время конфигурирования. Если такая проверка нужна, задавать отдельный явный emulator runner.
8. Кешировать host-tools по версиям, host ABI и рецепту. Object/cache директории разделять по архитектуре, sysroot/toolchain, target и опциям.
9. Python/SCons не включать в RPM редактора/игры: это инструменты сборки. Они попадут на устройство только при отдельно согласованной поддержке нативной разработки на нём.

Критерий эксперимента: на обеих архитектурах успешно пройти генерацию файлов upstream Godot, компиляцию и линковку с сохранением исходных требований SConstruct. Bootstrap решает проблему Python/SCons, но не гарантирует совместимость старого target-компилятора, libstdc++ или зависимостей: эти ограничения проверяются отдельно.

## SDK, PSDK и BT

Это способы предоставления окружения, а не разные runtime-платформы. Разделить выбор build environment и платформу SCons.

| Среда | Что подтверждено для savegame 4.4_auroraos | План нового порта |
|---|---|---|
| SDK с SB2 | Экспортёр явно использует sfdk либо SSH в build engine, sb2 и rpmbuild | Поддержать через отдельный адаптер |
| PSDK | Документация PSDK предусматривает sb2/mb2; отдельного адаптера PSDK в исследованной ветке не найдено | Поддержать прямой запуск в PSDK без жёстких путей SDK VM |
| BT | Интеграции apptool и явного BT toolchain в исследованной ветке не найдено | Поддержать явную cross-сборку в BT и независимую упаковку |

Нельзя утверждать, что savegame проверенно поддерживает все три среды. Возможность вручную собрать через SB2 не равна готовой интеграции экспортёра. Вывод относится к исследованной ветке, а не ко всем сторонним скриптам автора.

По документации apptool поддерживает qmake/CMake и ограничивает структуру spec. Не выдавать простой вызов SCons из spec или CMake-обёртки за подтверждённую поддержку apptool. Базовый BT-путь: явная сборка SCons с toolchain/sysroot, затем упаковка подготовленного staging через отдельный проверенный рецепт RPM. Интеграция с apptool — самостоятельный эксперимент. Для CMake-проекта GDExtension путь apptool потенциально естественнее, но тоже требует проверки.

Общий профиль окружения содержит host tools, target compiler, sysroot, pkg-config, ABI, runner и packaging backend. SDK/PSDK/BT должны выдавать одинаковый контракт артефактов.

## godot-cpp и GDExtension — обязательная часть

В KotDath/godot-cpp уже есть `4.4.1_auroraos`, коммит `3f8f6f3dfd70bb6ada2da342fbcdcd857a692fbf`. Проверены `tools/auroraos.py` и `cmake/auroraos.cmake`: отдельная платформа, PIC, `$ORIGIN` в SCons, флаги архитектуры и defines. Это исходный материал, не готовая совместимость с 4.7.2.

План адаптации:

- Выбрать и закрепить godot-cpp revision, поддерживающий API 4.7. Не считать текущий master пользовательского форка автоматически подходящим. Создать соответствующую ветку адаптации, предпочтительно `4.7.2_auroraos`.
- Согласовать `gdextension_interface.h` и `extension_api.json` с закреплённым движком; JSON можно выгрузить из собранного host-редактора той же ревизии. Зафиксировать хеш API, precision и build configuration в манифесте. Не требовать запуска ARM редактора ради генерации биндингов.
- Поддержать SCons `platform=auroraos` и CMake toolchain с эквивалентными настройками. Не дублировать разные политики ABI в двух системах.
- Один профиль compiler/sysroot/ABI для движка, godot-cpp, расширения и его частных зависимостей. Для ARM32 проверить hard-float ABI и допустимые CPU/FPU-флаги; одного `-march=armv7-a` недостаточно. Не включать NEON без требования профиля.
- godot-cpp по умолчанию статически включается в расширение с PIC; само расширение — ELF shared object. Не нужна линковка с исполняемым файлом Godot: взаимодействие идёт через GDExtension C API и entry point.
- Все включаемые статические библиотеки собирать с PIC. Экспортировать entry symbol; ограничить остальные символы, где это безопасно. Проверить видимость и C++ runtime ABI.
- Явно определить политику libstdc++/libgcc, exceptions, RTTI, precision и LTO. Не копировать статический C++ runtime по умолчанию без анализа. Базовый выбор — согласованный target runtime, разрешённый профилем системы; не передавать владение C++ объектами через границу библиотек произвольно.
- Проверить использование расширения в редакторе (tool-код) и в обоих шаблонах. Hot reload проверять отдельно; при его включении учитывать `-fno-gnu-unique`, уничтожение объектов, потоки и dlclose. Не обещать безопасную выгрузку произвольной внешней библиотеки.
- Подготовить небольшой шаблон проекта с SCons и CMake, регистрацией класса, методом для GDScript и внешней SO-зависимостью.

Пример соглашения для `.gdextension` (имена итоговых файлов согласовать с выбранным godot-cpp):

```ini
[configuration]
entry_symbol = "example_library_init"
compatibility_minimum = "4.7"

[libraries]
auroraos.debug.arm32 = "res://bin/arm32/libexample.debug.so"
auroraos.release.arm32 = "res://bin/arm32/libexample.release.so"
auroraos.debug.arm64 = "res://bin/arm64/libexample.debug.so"
auroraos.release.arm64 = "res://bin/arm64/libexample.release.so"
```

Добавить соответствующие `[dependencies]` для поставляемых библиотек. В проекте для Linux host-редактора нужны также Linux-бинарники расширения: ARM SO на x86_64 не загружается. Headless export проектов с tool-расширениями также включить в тесты.

## Линковка SO, загрузчик и RPM

Проверено в Godot 4.7.2: GDExtension выбирает библиотеки и dependencies по feature tags. Unix loader вызывает dlopen; fallback ищет файл рядом с executable и в `../lib`, используя basename. Это не обеспечивает произвольную раскладку частных библиотек и не заменяет разрешение транзитивных DT_NEEDED системным загрузчиком.

Предлагаемый контракт:

1. Экспортёр получает SharedObject-артефакты штатного pipeline экспорта и dependencies `.gdextension`, затем формирует манифест нативных файлов. Не ограничиваться поиском строк в ini и копированием главного SO.
2. `.so` размещаются физическими файлами вне PCK. Для game RPM использовать приватный каталог приложения, например `%{_libdir}/<app-id>/extensions/<extension-id>/`; окончательный путь проверить валидатором и согласовать с загрузчиком.
3. Сохранять однозначное соответствие `res://` пути и установленного файла. При необходимости экспортировать манифест отображения и реализовать его разрешение в OS_AuroraOS. Не полагаться на basename-fallback, допускающий коллизии. В режиме редактирования сначала работают реальные пути проекта.
4. Соседние частные библиотеки разрешать через относительный DT_RUNPATH `$ORIGIN` при допустимости выбранным профилем. У каждой библиотеки, имеющей свои DT_NEEDED, должен быть собственный корректный RUNPATH: RUNPATH родительского SO не наследуется транзитивно.
5. Если политика RPM запрещает выбранный RUNPATH, пересмотреть раскладку и согласовать альтернативную политику загрузки до выпуска. Абсолютный dlopen главного SO сам по себе не решает поиск его зависимостей. Не маскировать проблему глобальным LD_LIBRARY_PATH.
6. Проверять readelf: ELF class/machine, ARM ABI, SONAME, DT_NEEDED, RUNPATH, требуемые версии GLIBC/GLIBCXX/CXXABI. Сопоставлять с выбранным sysroot. Отсутствующую или чужую архитектуру отклонять при экспорте.
7. Рекурсивно анализировать DT_NEEDED: системные разрешённые зависимости превращаются в RPM Requires; частные включаются в пакет с нужными SONAME/symlink. Не копировать glibc, loader и случайные host-библиотеки. dlopen-зависимости, которых нет в DT_NEEDED, должны быть заявлены явно.
8. Не отключать глобально автоматический анализ зависимостей RPM. При необходимости фильтровать только частные Provides/Requires и проверять, что системные зависимости сохранились.
9. Каталоги по extension-id не гарантируют изоляцию одинаковых SONAME внутри процесса. Проверять конфликты; для несовместимых частных библиотек нужны уникальные SONAME и перелинковка либо отказ от совместной загрузки.
10. Проверять разрешения файлов, отсутствие build-host путей, лицензии, debug symbols и совместимость с профилем безопасности. Загрузка SO не обходит ограничения процесса или sandbox.

Обязательный интеграционный тест: extension → libA.so → libB.so. Работает в редакторе и экспортированной игре, после установки RPM на чистое устройство, без shell-переменных разработчика. Негативные тесты: отсутствующая libB, неверный ARM ABI, коллизия SONAME, несовпадение precision, отсутствующий entry point. Ошибка должна быть диагностируемой.

## Редактор, экспорт и артефакты

Редактор на Авроре: Project Manager, импорт, сохранение, кириллица и экранная клавиатура, файловые диалоги, popup-меню, масштабирование, touch/мышь, запуск/остановка проекта, возврат из игры. Проверить ограничения запуска subprocess и loopback-отладки внутри выбранного профиля. Однооконный режим — начальный default, а не замена реализации диалогов и жизненного цикла.

Разделить экспорт на проверку preset → PCK/staging → нативные зависимости → spec/desktop/icons → RPM → валидация/подпись → установка/запуск. GUI и CLI используют общий код. Подпись — отдельный этап, без паролей в preset, command log и репозитории. Игра и редактор имеют разные минимально необходимые разрешения.

Обязательные артефакты: редактор, template_debug и template_release для ARM32 и ARM64; Linux-редактор с Aurora exporter; пример GDExtension и его библиотеки для обоих ARM; тестовый game RPM каждой архитектуры. Манифест релиза связывает engine commit, godot-cpp commit/API hash, toolchain/sysroot fingerprint и build flags.

## Последовательность реализации и критерии

1. Инвентаризация окружений и bootstrap Python/SCons. Минимальный cross C++/SO проект и генераторы Godot работают в SDK/PSDK/BT; каждую среду отмечать проверенной отдельно. Получить capabilities устройств без выбора архитектуры порта по номеру ОС.
2. Ветка движка от 4.7.2-stable, каркас platform=auroraos, шесть ARM сборок, headless smoke. ARM32 включить сразу. Параллельно по смыслу этапов, без требования агентной параллельности: закрепить godot-cpp/API и собрать минимальное расширение.
3. Ограниченное выделение общего Wayland, Aurora shell, EGL/GLES. 2D и 3D сцена выводятся на устройствах; Linux Wayland не регрессирует.
4. Ввод, ориентация, жизненный цикл, звук, пути данных. Проверить фон/возврат, блокировку, resize и отмену touch.
5. Полный цикл редактора на обеих архитектурах. Загрузка GDExtension и tool-кода обязательна на этом этапе.
6. Экспортёр, SO resolver, манифест зависимостей, RPM backend для окружений. Проверить цепочку SO после чистой установки, debug/release и host headless export.
7. Vulkan и дополнительные возможности по аппаратным результатам; оптимизация памяти ARM32, GDExtension hot reload и внешний экран с явной матрицей поддержки.
8. CI, документация, подписанные артефакты и публикация в пользовательских форках. Релизные теги движка вида `4.7.2-auroraos.1`, связанный godot-cpp commit указан в манифесте.

## Проверки и сопровождение

- Тематические коммиты: bootstrap, build platform, общий Wayland, Aurora runtime, графика, editor, godot-cpp, packaging, tests/docs. Сохранять авторство заимствованных изменений.
- CI: шесть ARM-артефактов, host editor/export, обычный Linux Wayland, SCons/CMake GDExtension, ELF/RPM проверки. Полную матрицу сред расширять по мере их фактической проверки.
- Аппаратные испытания обоих ARM: 2D/3D, input/IME, ориентация, звук, фон/возврат, сохранения, полный цикл редактора, расширения и цепочки зависимостей. Эмулятор не заменяет libhybris/GPU проверки.
- Не выдавать успешную компиляцию за работу редактора, успешную загрузку SO за корректную упаковку, а поддержку SDK/SB2 за поддержку BT/apptool.
- Незакрытые вопросы: конкретные устройства, доступные SDK/PSDK/BT targets, допустимая политика RUNPATH/RPM, target compiler ABI, протокол экранной клавиатуры. Версия ОС вторична для проектирования, но фиксируется в протоколах тестирования.
