# План дальнейшей реализации Godot для Aurora OS

Дата: 2026-10-23. Основа: обсуждение после коммита d7517648d1.
Это план реализации; наличие пункта не означает, что возможность уже работает.
Фактические результаты проверок находятся в STATUS.md.

## Решения пользователя и порядок работ

Приоритеты, по исходной нумерации обсуждения:
**6 → 5 → 7 → 1 → 2 → 3 → 4 → 8 → 9 → 10 → 11 → 12 → 13**.

- Не выделяем и не пишем новый общий Wayland-слой. Сохраняем минимальные изменения
  оригинальной Linux-сборки. Переиспользуем существующий backend; Aurora-логику
  размещаем в platform/auroraos. Необходимые точки интеграции должны быть узкими,
  изолированными и не менять поведение Linux. Перенос файлов из linuxbsd отменён.
- Не привязываем продукт к audb. audb используется для наших аппаратных проверок.
- Vulkan и остальные обсуждавшиеся функции не исключены из плана.
- Для каждого аппаратного ограничения фиксируем причину и условие продолжения.
  Нельзя выдавать компиляцию за аппаратную поддержку. Независимая работа может
  продолжаться, если следующий шаг приоритетного пункта требует внешних условий.

## 1. Удалённая отладка без зависимости от audb

Используем штатный отладчик Godot: игра на Авроре устанавливает TCP-соединение
с редактором на ПК. Экспортёр использует gen_export_flags(), а параметры доходят
до процесса игры. Обычный экспорт отклоняет launch flags; Remote Deploy передаёт их процессу
через gen_export_flags(). Результаты проверок и ограничения — в STATUS.md.

Два сценария: ручной экспорт/установка/запуск с адресом отладчика и запуск из
редактора через выбранные средства SDK. Адрес — параметр запуска, не обязательная
часть RPM. Для запуска через иконку можно предусмотреть development-конфигурацию;
в обычный release она автоматически не переносится. Установка и отладка независимы.

Проверки: GDScript breakpoint, шаги, переменные, Remote Scene Tree, ошибки,
профилирование, повторное соединение. Штатный аргумент: --remote-debug.
C++-отладка GDExtension — отдельный сценарий: debug symbols, согласованный sysroot,
доступный SDK способ подключения GDB. Отладчик GDScript не заменяет GDB.
Для проверки с пользовательским ПК нужны его доступный адрес и запущенный редактор;
доступность native debugging сначала исследуем на устройстве.

## 2. Подпись, установка и запуск из ПК-редактора

Последовательность: PCK/SO → RPM → валидация → подпись → установка → запуск.
Операции вызываются отдельно; экспорт не требует подключённого устройства.
Первый кандидат для управления устройством — штатные средства SDK/sfdk; конкретные
команды и возможности подтверждаем в установленной версии. audb не обязателен.

Пути к инструментам и подключения — настройки редактора. Метаданные приложения
и архитектура — export preset. Секреты/пароли не сохраняются в проекте.
Подпись — отдельный этап с информацией о сертификате, состоянии подписи и проверке.
Для защищённого ключа — безопасный интерактивный ввод, не пароль в аргументах.
Проверки: новая установка, обновление, неверная подпись, потеря связи, повторный
запуск и остановка только своего процесса.

## 3. Полный цикл редактора на Авроре

Создание проекта → импорт → редактирование сцены/скрипта → сохранение → запуск игры
→ остановка → возврат. Проверяем writable paths проектов/настроек/кеша, файловые
диалоги, popup, scale, touch/мышь, физическую и экранную клавиатуру, сохранность
после перезапуска, отдельный игровой процесс и связь с отладчиком.
Проверяем GDExtension tool-классы и editor plugins.

Отдельно проверяем ограничения профиля на subprocess и loopback. Сначала надёжное
отдельное окно игры; встраивание — после проверки возможностей compositor.
Полный редактор не подразумевает автоматически компиляцию C++ или RPM на устройстве.

Проверено на KVADRA ARM64: создание проекта/сцены, сохранение, ввод GDScript
с кириллицей, запуск/остановка отдельной игры. После импорта в постоянный каталог
приложения цикл работает также из штатной оболочки/sandbox: сохранение переживает
обновление RPM, loopback debugger и Remote Scene Tree работают. EditorPlugin
вызывает нативную цепочку из RPM и получает 42. Исправлены размер окна/viewport
и каталоги данных/настроек/кеша. Для редакторского RPM нужен `Internet`, включая
локальные TCP-сокеты. Автоматическое поднятие дочернего окна, перекрытие диалогов
клавиатурой и расширенные сценарии редактора ещё требуют работы.
См. [editor_smoke/README.md](editor_smoke/README.md) и [STATUS.md](STATUS.md).

## 4. Полный IME и экранная клавиатура

Исходный адаптер поддерживал ввод без синхронизации редактируемого контекста.
Пункт включает окружающий текст, курсор/выделение, preedit, замену/удаление диапазонов,
сброс при смене поля и потере фокуса. Предлагается небольшой общий интерфейс
контекста редактирования из LineEdit/TextEdit/CodeEdit в платформенный слой;
text-input-v2 остаётся Aurora-адаптером. Изменения общего UI обосновываются отдельно.

Преобразовываем байтовые индексы UTF-8 протокола в индексы Godot. Проверяем кириллицу,
emoji, составные символы, выбор/замену слова, подсказки, многострочность, смену полей.
Парольные поля не передают лишний контекст.

**Выполнена первая часть:** Aurora передаёт IME commit целиком в активный
LineEdit/TextEdit/CodeEdit через небольшой внутренний DisplayServer callback.
Остальные backend сохраняют прежнюю обработку; общий Wayland слой не выделялся.
Сообщение запоминает получателя и поколение фокуса; вызов UI происходит на главном
потоке после предшествующих событий ввода. Пустой commit не удаляет выделение.
На KVADRA проверены точные переносы строк/табуляция, кириллица/emoji, замена
выделения, Undo одной операцией, сигнал LineEdit при замене той же длины,
обычный ввод/Backspace и запрет редактирования. Проверочный проект и анализатор
журнала: `misc/aurora/ime_smoke/`.

**Выполнена вторая часть:** актуальный bounded surrounding text с курсором/anchor,
удаление/замена диапазонов вне выделения, изменение позиции после commit,
проверка границ UTF-8 и снимка контекста. Обновления обычного IME отделены от
внешних изменений текста/каретки; reset использует `wl_display_sync` и отбрасывает
устаревшие события. Парольные поля передают пустой контекст. Контекст больше
1000 Unicode-символов и несколько кареток не используются для расширенных IME
операций; обычная вставка продолжает работать. Общий Linux backend не меняет
поведение. Архитектура и контракт: `misc/aurora/IME.md`.

Проверены 47 C++ assertions; набор TextEdit прошёл 4235 проверок. На KVADRA
Maliit подтвердил текст/курсор после каждого символа, включая emoji и переводы
строк; wire trace подтвердил UTF-8 позиции и отсутствие текста пароля.

**Третья часть реализации:** preedit commit fallback хранится у своего текстового
клиента; поддержаны пустой fallback, скрытая каретка и именованные Unicode-диапазоны
стилей. Прямоугольник каретки и вся область клавиатуры преобразуются с учётом
поворота; высота landscape-клавиатуры больше не берётся из исходной surface height.
ScriptEditor получает отступ над клавиатурой с учётом масштаба viewport.
Проверены 72 C++ assertions, сборки editor ARM32/ARM64, высота клавиатуры
и отступ ScriptEditor в sandbox на KVADRA (RPM 4.7.2-11). Базовый Linux Wayland
3D/GDExtension smoke также прошёл. Оставшиеся ограничения — в STATUS.md.

**Выполнена четвёртая часть:** при уходе окна в фон native preedit завершается
сохранённым fallback, а не исчезает. Callback привязан к полю и поколению фокуса;
задержанный callback старого поля не отключает IME нового. Обычные текстовые поля
разрешают completion/correction, CodeEdit запрещает; тип парольной клавиатуры
скрывает контекст независимо от визуальной маски. На KVADRA штатный тестовый
обработчик Maliit подтвердил preedit → фон → commit → один Undo. Тестовая раскладка
удалена, настройки восстановлены. Это проверка протокола, не приёмка языковой IME.

**Далее:** аппаратная приёмка языковой композиции/подсказок, preedit поверх
выделения, диалоги над клавиатурой и
положение candidate UI при прокрутке/повороте.
Пункт 4 целиком пока не закрыт. После него сохраняется приоритет пункта 8.

## 5. Жизненный цикл, touch и звук

Явно различаем фокус, видимость, сворачивание, блокировку и возобновление.
Потеря фокуса не равна полной остановке. Согласуем отмену касаний, IME, остановку
ненужной отрисовки, восстановление поверхности/ресурсов и аудиополитику.

Основа звука — существующий PulseAudio. Проверяем воспроизведение, задержку, смену
выхода, наушники, прерывания и восстановление потока. Интеграция управления
аудиоресурсами — по фактически доступным Aurora API.
Touch: несколько пальцев, drag, поворот в жесте, потеря фокуса. Lifecycle:
повторная блокировка, длительный фон, возврат без утечек и зависаний.

## 6. Vulkan — первый приоритет

На старте vulkan=yes явно запрещён Aurora detect.py. Этапы:
1. Проверить loader, ICD/GPU, расширения и ограничения отдельно для ARM32/ARM64.
2. Минимальный probe: Wayland surface, Vulkan instance/device и swapchain.
3. Подключить существующий Vulkan/RenderingDevice Godot без изменения Linux-политик.
4. Проверить Mobile, затем Forward+ на подходящем оборудовании.
5. Resize, поворот, сворачивание, пересоздание swapchain, восстановление.

Поворот GLES нельзя копировать вслепую: согласуем currentTransform,
supportedTransforms и preTransform, исключая двойной поворот. GLES остаётся
доступным. Автоматический fallback не гарантирует сохранность Vulkan-only эффектов;
политику выбора рендерера нужно задавать явно.
Критерии: 2D/3D, материалы, необходимые compute-возможности, поворот, фон/возврат,
длительная работа без device loss. Название Mali не доказывает доступность Vulkan
в поставленном OS graphics stack. Отсутствующий драйвер не заменяется loader-ом.

## 7. Raycast/Embree и occlusion culling

Отключённый module_raycast не означает отключение физических RayCast3D.
Текущий modules/raycast/config.py допускает ARM64, но не ARM32.
ARM64: включить Embree, решить build/ABI проблемы, проверить culling и стоимость.
ARM32: после анализа выбрать явно неподдерживаемую возможность либо поддерживаемый
альтернативный backend. Просто убрать архитектурную проверку недостаточно;
альтернативный backend является существенной самостоятельной работой.
Критерий: закрытые объекты исключаются, видимые не исчезают, CPU/RAM оправданы.

## 8. GDExtension, раскладка SO и hot reload

Базовая цепочка SO работает. Для plugin-подкаталогов сохраняем структуру и вводим
однозначное соответствие project path → установленный файл; у каждой SO свой
RUNPATH. Разные каталоги не устраняют конфликт одинаковых SONAME в одном процессе.

Hot reload использует механизм Godot и поддержку пересоздания объектов godot-cpp.
Перед выгрузкой нужны освобождение ресурсов, остановка потоков и снятие callbacks.
Отдельно проверяем доставку новой SO в рамках политики ОС: writable-каталог не
гарантирует разрешённую загрузку. ПК-редактор и установленное Aurora-приложение
получают отдельные статусы поддержки. Проверяем многократное обновление без старого
кода/потоков и падений; несовместимые изменения требуют перезапуска.

## 9. Несколько окон, внешние экраны и заставка

Ориентация сейчас рассчитана на главное окно. Для расширения храним размер, scale,
transform, фокус, surface по каждому окну/output. Отслеживаем подключение/отключение
экранов, выбираем output, создаём окна только при поддержке shell, отдельно
обрабатываем popup/transient. Встроенные диалоги остаются рабочим fallback.
Заставка проходит через тот же механизм ориентации, что и кадр.
Для проверки нужен внешний экран с подходящим подключением; возможности зависят
от compositor. Не выдаём доступность API за возможность физического расширения экрана.

## 10. XR

Сначала проверяем совместимый OpenXR runtime на конкретной Авроре. Модуль Godot
не заменяет runtime. При наличии: loader/module, graphics binding, session,
eye swapchains, tracking, controllers. Если runtime отсутствует, его портирование
— отдельный подпроект, а не небольшая правка Godot.
Нужны конкретное XR-устройство и подключение. Мобильный поворот экрана не должен
применяться к изображениям глаз: у XR отдельное представление.

## 11. SDK, PSDK, BT и ARM32

Общий контракт: host Python/SCons + target compiler/sysroot/ABI → артефакты.
Различается runner среды. Генераторы запускаются на host, движок/расширения
компилируются для ARM. Python/SCons не попадают в игровой RPM.
BT/apptool проверяется отдельно: CMake-обёртка SCons сама по себе не доказательство.
ARM32: hard-float ABI, инструкции CPU, память, большие импорты, SO на реальном
устройстве, которое пользователь предоставит позднее.
Матрица: editor/debug/release обеих ARM, godot-cpp SCons/CMake, RPM и реальные
запуски. Для каждой среды самостоятельный статус.

## 12. Windows/macOS как хосты

Две части: ПК-редактор с Aurora exporter и доступ к среде упаковки/проверки RPM.
Упаковщик получает явные входные файлы и возвращает артефакт/диагностику.
Первый backend — Linux/SDK. Проверяем наличие SDK-средств на остальных хостах;
при отсутствии локальной упаковки рассматриваем явно настроенную Linux build-среду.
Проверяем пробелы в путях, передачу файлов, отмену, инструменты и выбор ARM SO.
Наличие вкладки Export не означает полный локальный export pipeline.

## 13. Сопровождение и CI; общий Wayland не выделяем

В предыдущем предложении планировалось вынести общий Wayland из linuxbsd.
Пользователь отказался от этого изменения: не выполняем перенос и не создаём новый
общий backend. Сохраняем platform/auroraos и минимальные условные hooks.
Проверки исходного Linux Wayland и Aurora обязательны при изменении общих файлов.

CI: шесть ARM-артефактов, godot-cpp/пример SCons+CMake, ELF/DT_NEEDED/RPM,
настольные проверки и отдельные аппаратные проверки. Манифест связывает engine,
godot-cpp, API, SDK/sysroot и build flags. Секреты подписи вне репозитория.
Компиляция и аппаратный запуск отражаются раздельно.
